# Prototype Builder

ทักษะนี้แปล Requirement + Backlog + Feature List + User Journey ของ Local Story Hub ที่มีอยู่
แล้วให้เป็นหน้าจอ HTML **แบบ Interactive** (เปิดในเบราว์เซอร์ได้ทันที) โดยยึดโทนสีและคอมโพเนนต์
จาก DESIGN.md เสมอ — **prototype ที่สร้างต้องมีพฤติกรรมจริงเสมอ ไม่ใช่แค่ mockup นิ่ง ๆ** (ดู
นิยาม "Interactive baseline" ในขั้นตอนที่ 7)

`docs/` เป็นส่วนหนึ่งของ Obsidian vault ที่ root ของ repo (`newLinkFormat: relative`,
`useMarkdownLinks: false`) — ทุกลิงก์ระหว่างเอกสาร Markdown ต้องเป็น wikilink แบบ relative
path เท่านั้น

## เมื่อไรควรมอบงานต่อให้ agent `prototype-builder`

ถ้าขอบเขตกว้าง (ทำทั้งระบบ) หรือต้องการให้ทำงานแบบแยกบริบท ให้เรียกใช้ผ่าน Agent tool ด้วย
`subagent_type: prototype-builder` แทนการทำตามขั้นตอนด้านล่างเอง ทักษะนี้และ agent ใช้วิธีการ
เดียวกัน

## หลักการทั่วไป: เมื่อไม่ชัดเจน ให้ถามพร้อมทางเลือก

ทุกจุดที่ต้องตัดสินใจแทนผู้ใช้ (ขอบเขต, การสร้าง version ใหม่หรือแก้ของเดิม, แนวทางเมื่อไม่มี
DESIGN.md ฯลฯ) **ห้ามเดาและลงมือทำเอง** — ให้ถามผู้ใช้พร้อมเสนอ **อย่างน้อย 3 ทางเลือก** ทุก
ทางเลือกต้องมีข้อดี/ข้อเสียกำกับ เพื่อให้ผู้ใช้ตัดสินใจได้ง่าย

## ขั้นตอน

### 1. กำหนดขอบเขต (Scope)

ถ้าผู้ใช้ระบุขอบเขตมาชัดเจนแล้ว ให้ใช้ตามนั้น ถ้าไม่ได้ระบุ ให้ถามว่าต้องการทำ prototype
ครอบคลุมทั้งระบบ หรือเจาะจงเฉพาะ persona/journey/feature ใดหนึ่ง (ระบุตัวเลือกจริงที่มีอยู่ใน
โปรเจกต์ตอนนี้ให้เลือก ไม่ใช่ถามลอย ๆ)

### 2. เช็ค DESIGN.md ก่อนเสมอ

อ่าน `docs/02-design/01-prototypes/DESIGN.md` — **ถ้ายังไม่มีไฟล์นี้ ห้ามสร้าง prototype
ต่อโดยเดาโทนสี/สไตล์เอง** ให้หยุดแล้วถามผู้ใช้เพื่อเก็บข้อมูลก่อน โดยเสนอทางเลือกอย่างน้อย
3 แบบ:
1. ผู้ใช้อธิบายโทนสี/สไตล์ที่ต้องการเป็นคำพูด
2. ผู้ใช้ส่งภาพตัวอย่าง/โลโก้/reference มาให้ยึดตาม
3. ให้ agent เสนอแนวทางตามบริบทของ spec มาให้เลือก 2-3 แบบก่อน

เมื่อได้ข้อมูลจากผู้ใช้แล้ว ให้สร้าง `DESIGN.md` ตามโครงสร้างเดียวกับที่ใช้อยู่ในโปรเจกต์นี้
(Brand Identity & CI, Design Tokens: Colors/Typography/Spacing, UI Components & Pattern) แล้ว
จึงกลับมาทำขั้นตอนถัดไป

### 3. รวบรวมต้นทาง

อ่านตามขอบเขตที่กำหนดในข้อ 1: spec ที่เกี่ยวข้องใน `docs/01-requirements/01-spec/`,
`docs/01-requirements/03-task/product-backlog.md`,
`docs/01-requirements/03-task/feature-list.md` (ถ้ายังไม่มี แจ้งผู้ใช้ว่าควรรัน
`feature-list` ก่อน แต่ยังทำ prototype ต่อได้โดยอิง backlog ตรง ๆ ถ้าผู้ใช้ยืนยัน), และ User
Journey ที่เกี่ยวข้องใน `docs/02-design/01-prototypes/*.md`

### 4. เช็ค Open Questions ที่กระทบขอบเขตนี้

อ่าน `docs/01-requirements/03-task/open-questions.md` เหมือนที่ skill `user-journey` ทำ —
ถ้ามี Open Question กระทบหน้าจอที่จะสร้าง ต้องแจ้งผู้ใช้และถามว่าจะสร้างแบบ DRAFT ต่อไปเลย
หรือรอคำตอบก่อน — ห้ามข้ามขั้นตอนนี้

### 5. เสนอแผนก่อนลงมือสร้างเสมอ (บังคับ)

ก่อนสร้างไฟล์ใด ๆ ต้องสรุปแผนให้ผู้ใช้ตรวจสอบและยืนยันก่อนเสมอ ระบุ: หน้าจอที่จะสร้างทั้งหมด
พร้อมชื่อไฟล์, แต่ละหน้าจออ้างอิงจาก journey/FR/BL อะไร, คอมโพเนนต์จาก DESIGN.md ที่จะใช้,
**พฤติกรรม Interactive ที่จะใส่ในแต่ละหน้าจอ** (ฟอร์มไหน validate, ปุ่มไหนมีผลลัพธ์จริง, จุด
ไหนจำ state ข้ามหน้าด้วย `localStorage`, มีส่งข้อมูลข้ามหน้าจอไหม — ดูรายการฐานในข้อ 7), จุด
ที่เป็น DRAFT (ถ้ามี), และจะเก็บที่ folder version ไหน (ดูข้อ 6) **ห้ามลงมือสร้างไฟล์จริง
จนกว่าผู้ใช้จะยืนยันแผนนี้**

### 6. ตัดสินใจเรื่อง Folder Version (ถามทุกครั้งที่มีเวอร์ชันเดิมอยู่แล้ว)

List โฟลเดอร์ใน `docs/02-design/01-prototypes/prototype-v*/` ก่อนเสมอ:

- **ไม่มีโฟลเดอร์ version ใดเลย** → สร้าง `prototype-v1/` ได้เลย ไม่ต้องถาม
- **มี version อยู่แล้ว** → **ต้องถามผู้ใช้ทุกครั้งไม่มีข้อยกเว้น**:
  1. **สร้าง version ใหม่** (`prototype-v{N+1}/`) — แนะนำเมื่อเปลี่ยน requirement อย่างมี
     นัยสำคัญ/เพิ่ม persona ใหม่/ต้องการเก็บของเดิมไว้เทียบ ข้อดี: ประวัติไม่หาย เทียบก่อน-หลัง
     ได้ ข้อเสีย: มีหลายโฟลเดอร์ต้องดูแล
  2. **แก้ไข version ล่าสุด** — แนะนำเมื่อปรับแก้เล็กน้อย/แก้บั๊กดีไซน์ ข้อดี: ไม่มีไฟล์ซ้ำซ้อน
     ข้อเสีย: เวอร์ชันก่อนแก้หายไป (เว้นแต่ git history ยังเก็บไว้)
  3. ถามผู้ใช้ตรง ๆ ว่ามีเหตุผลอื่นที่อยากตัดสินใจต่างจาก 2 ข้อข้างต้นหรือไม่

  ให้คำแนะนำเบื้องต้นตามลักษณะงาน แต่**ให้ผู้ใช้เป็นผู้ตัดสินใจสุดท้ายเสมอ**

### 7. สร้างไฟล์ Prototype

แต่ละหน้าจอเป็นไฟล์ HTML แยก (self-contained: inline CSS + inline JavaScript (vanilla ไม่ใช้
library ภายนอก) ในไฟล์เดียว เปิดตรงจากเบราว์เซอร์ได้โดยไม่ต้อง build, ไม่พึ่ง CDN ภายนอกยกเว้น
ฟอนต์ Google Fonts) ใช้ CSS variable ตาม token ใน `DESIGN.md` แปลงเป็น CSS custom properties
จริง ตั้งชื่อไฟล์ตาม screen/journey step ที่สื่อความหมาย บันทึกที่
`docs/02-design/01-prototypes/prototype-v{N}/` พร้อมสร้าง `prototype-v{N}/README.md` สรุปแผน
ที่ยืนยันแล้ว (จากข้อ 5) พร้อม wikilink กลับไปยัง journey/spec/backlog ต้นทางของแต่ละหน้าจอ
และสรุปพฤติกรรม Interactive ที่ใส่ไว้ต่อหน้าจอ (ดูตัวอย่างรูปแบบใน `prototype-v1/README.md`)

**Interactive baseline — ทุก prototype ที่สร้างต้องมีอย่างน้อยเท่าที่เกี่ยวข้องกับหน้าจอนั้น
(เป็นค่าเริ่มต้น ไม่ใช่ทางเลือก เว้นแต่ผู้ใช้ขอให้ทำ static ในแผนที่ตกลงกันไว้):**

1. **ปุ่ม/การกระทำต้องมีผลลัพธ์จริงเมื่อกด** — ห้ามมีปุ่มที่กดแล้วไม่เกิดอะไรขึ้นเลย จำลองการ
   ประมวลผล (เช่นปุ่ม AI) ด้วย loading state สั้น ๆ แล้วโชว์ผลลัพธ์จริง
2. **จุดที่ journey มี decision/ทางแยก ต้องมี UI ให้เลือกจริงและเห็นผลต่างกันตามที่เลือก**
3. **State ที่ควรอยู่ข้ามการโหลดหน้า ให้ persist ด้วย `localStorage`** แล้วสะท้อนสถานะในหน้าอื่น
   ที่เกี่ยวข้องด้วย
4. **ถ้า journey มีการสร้าง/ส่งข้อมูลที่ควรไปปรากฏในอีกหน้าจอหนึ่ง ให้จำลอง data flow นั้นจริง**
   ผ่าน `localStorage` ระหว่างหน้าจอ ไม่ใช่แค่ redirect เฉย ๆ
5. **ฟอร์มต้อง validate ก่อนดำเนินการจริง** พร้อมข้อความแจ้งข้อผิดพลาดที่อ่านเข้าใจง่าย ไม่ใช่
   alert ทั่วไป
6. **ช่องค้นหา/กรองข้อมูล ต้องกรองผลลัพธ์แบบ live จริง** พร้อม empty state เมื่อไม่พบผลลัพธ์

ถ้าหน้าจอไหนไม่มีจุดที่เข้าเงื่อนไขข้างต้นเลย ก็ไม่ต้องฝืนใส่ interactivity ที่ไม่มีเหตุผลรองรับ
ใน journey/requirement

### 8. เชื่อมโยงกลับ (bidirectional link) และรายงาน

เพิ่ม wikilink ใน `docs/02-design/01-prototypes/index.md` ชี้ไปยัง `prototype-v{N}/README.md`,
เพิ่ม wikilink ย้อนกลับจาก journey/spec ที่ใช้ (append เท่านั้น ห้ามลบของเดิม), บันทึกลง
`docs/05-log/index.md` (version ไหน, กี่หน้าจอ, อ้างอิงอะไร, จุดไหน DRAFT) แล้วสรุปให้ผู้ใช้
ทราบพร้อม path เต็มสำหรับเปิดไฟล์ HTML ดู (ลิงก์ในแชทอาจเปิดไม่ได้ถ้าอยู่นอก working directory
หลัก)

## ข้อควรระวัง

- ห้ามสร้าง prototype โดยไม่มี DESIGN.md รองรับ
- ห้ามข้ามขั้นตอนเสนอแผน (ข้อ 5) หรือถามเรื่อง folder version (ข้อ 6) ไม่ว่าผู้ใช้จะขอให้
  "ทำเลย" ก็ตาม — อย่างน้อยต้องแจ้งแผนสั้น ๆ ให้เห็นก่อนเริ่มเขียนไฟล์
- ห้ามเดา requirement ที่ไม่มีอยู่จริง ถ้าจุดไหนไม่มีข้อมูลรองรับให้ถามผู้ใช้แทนการเดา
- ห้ามลบหรือแก้ไข prototype version เดิมโดยไม่ถูกขอ
- เอกสารในโปรเจกต์นี้เขียนเป็นภาษาไทย (ยกเว้นโค้ด/ชื่อไฟล์ที่ต้องเป็นภาษาอังกฤษ)

## หลังทำงานเสร็จ ให้สรุปให้ผู้ใช้ทราบ

- Prototype version ที่สร้าง/แก้ไข และเหตุผลที่เลือก
- รายชื่อหน้าจอที่สร้าง พร้อม path เต็มสำหรับเปิดดู
- จุดที่ยังเป็น DRAFT เพราะ Open Question ยังไม่ปิด
