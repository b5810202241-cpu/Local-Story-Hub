# ผลทดสอบ — นิสิต สมัคร/อนุมัติบัญชีผู้ใช้ใหม่ (TC-027 ถึง TC-032)

ทดสอบผ่านเบราว์เซอร์จริง (Playwright MCP) กับเว็บที่ deploy จริงที่ [https://lsh-nammon.web.app/](https://lsh-nammon.web.app/) (production Firebase project `lsh-nammon`) ตามขอบเขตที่ได้รับมอบหมาย — เฉพาะ **TC-027 ถึง TC-032** (หมวด "นิสิต — สมัคร/อนุมัติบัญชีผู้ใช้ใหม่") ใน [[../01-test-plan/test-plan|test-plan]] เท่านั้น ทดสอบเป็นชุดเดียวกันตามลำดับเหตุการณ์จริง (สมัคร 2 บัญชี → อาจารย์เห็นแจ้งเตือน → อนุมัติ 1 บัญชี → ไม่อนุมัติอีก 1 บัญชีพร้อมเหตุผล)

- **วันที่ทดสอบ**: 2026-09-23
- **ผู้ทดสอบ**: QA agent (จำลองผู้ใช้มือใหม่ ทดสอบผ่าน UI จริงทั้งหมด ไม่อ่าน source code เพื่อสรุปผล)
- **บัญชีทดสอบที่ใช้**: สมัครบัญชีนิสิตทดสอบใหม่ 2 บัญชีผ่านฟอร์มจริงที่ `student-publish.html` ตามที่ได้รับมอบหมาย ("ทดสอบ QA นิสิตอนุมัติ" สำหรับเส้นทางอนุมัติ, "ทดสอบ QA นิสิตปฏิเสธ" สำหรับเส้นทางปฏิเสธ) แล้วดำเนินการอนุมัติ/ปฏิเสธด้วยบัญชีอาจารย์ (`u004@example.com` จาก `LSH/DEMO_CREDENTIALS.md`) ผ่าน `admin-review-student-work.html` — ดูรายละเอียดที่หัวข้อ "ข้อมูลทดสอบที่สร้างไว้ในระบบ" ด้านล่าง

## บั๊กที่พบ

**ไม่พบบั๊กในขอบเขต TC-027 ถึง TC-032** — ทุก Then ที่ทดสอบได้เป็นจริงครบถ้วน รวมถึงจุดที่ต้องระวังเป็นพิเศษ (ข้อความแจ้งบัญชีถูกปฏิเสธที่ TC-029/TC-032) ซึ่งเป็น pattern เดียวกับบั๊กที่เคยพบซ้ำ 2 ครั้งในรอบก่อน (TC-022 คำขอแก้ไขชุมชน, TC-026 ผลงานนิสิต — ทั้งสองกรณีคือ "ฝั่งผู้ยื่นคำขอไม่เคยเห็นสถานะ/เหตุผลตอนถูกปฏิเสธ") **รอบนี้ไม่พบปัญหาเดียวกัน** — ฝั่งนิสิตที่บัญชีถูกปฏิเสธเห็นเหตุผลชัดเจนและสม่ำเสมอทุกครั้งที่ทดสอบซ้ำ (รีเฟรช, login ใหม่, navigate ไป-กลับหน้าอื่น) ต่างจากฝั่งชุมชน (TC-019 รอบก่อน) ที่พบข้อสังเกตความรุนแรงต่ำเรื่องข้อความไม่สอดคล้องกันเมื่อ navigate ตรงไปหน้าอื่นที่ไม่ใช่หน้า login — จุดนี้ฝั่งนิสิตไม่มีปัญหาเดียวกันเพราะ `student-publish.html` เป็นทั้งหน้า login และหน้าแสดงสถานะบัญชีในไฟล์เดียวกัน (ไม่มีหน้าอื่นแยกต่างหากแบบ `community-dashboard.html`/`community-create-content.html` ที่ต้อง guard สถานะซ้ำ)

TC-030 ไม่นับเป็นบั๊ก — เป็นข้อจำกัดที่ทราบอยู่แล้วล่วงหน้า (ยังไม่มี Notification Service ส่งอีเมลจริงตามที่ตัดสินใจข้ามไปก่อน) มีกลไกทดแทน (แบนเนอร์) ที่ทำงานถูกต้องแทน

## ข้อมูลทดสอบที่สร้างไว้ในระบบ

- **บัญชีนิสิตทดสอบที่ 1 (เส้นทางอนุมัติ)**:
  - อีเมล: `qa-tester-student-approve-lsh@example.com`
  - รหัสผ่าน: `QaTester1234!`
  - ชื่อ-นามสกุล: `ทดสอบ QA นิสิตอนุมัติ`
  - สถานะ: อนุมัติแล้ว (อนุมัติเองผ่าน `admin-review-student-work.html` ด้วยบัญชีอาจารย์ `u004@example.com`)
  - เก็บอยู่ใน Firebase Authentication + Firestore collection `users` (`role: 'student'`, `status: 'อนุมัติแล้ว'`) ของ project `lsh-nammon` จริง — ไม่มีปุ่มลบบัญชีตัวเองใน UI จึงปล่อยบัญชีนี้ค้างไว้ในระบบ
  - **ผลงาน 1 รายการที่ส่งขออนุมัติ** ใน collection `LSHRequests` (สร้างเพื่อยืนยัน TC-031 ว่าใช้ฟีเจอร์หลักได้จริง): หัวข้อ "ทดสอบ QA - ทดสอบสิทธิ์บัญชีนิสิตที่อนุมัติแล้ว (TC-031)", ชุมชนที่เลือก: "ชุมชนทดสอบผาบ่อง QA", สถานะ: "รอพิจารณา" (ยังไม่ได้กดอนุมัติ/ไม่อนุมัติ เก็บไว้เป็นหลักฐานตามธรรมเนียมเดิม) — ยืนยันคงอยู่จริงหลังตรวจซ้ำที่หน้าอาจารย์
- **บัญชีนิสิตทดสอบที่ 2 (เส้นทางปฏิเสธ)**:
  - อีเมล: `qa-tester-student-reject-lsh@example.com`
  - รหัสผ่าน: `QaTester1234!`
  - ชื่อ-นามสกุล: `ทดสอบ QA นิสิตปฏิเสธ`
  - สถานะ: ไม่อนุมัติ (ปฏิเสธเองผ่าน `admin-review-student-work.html` ด้วยบัญชีอาจารย์ `u004@example.com`, เหตุผลที่บันทึกไว้: "ทดสอบ QA: ข้อมูลในผลงานไม่ครบถ้วน (เหตุผลจำลองสำหรับทดสอบ TC-032)")
  - เป็นสถานะสิ้นสุดตาม Business Rule ของ BL-019/BL-020 — ใช้งานต่อไม่ได้ ต้องสมัครบัญชีใหม่เท่านั้น ปล่อยค้างไว้ในระบบเป็นหลักฐานการทดสอบ (ไม่มีปุ่มลบบัญชีใน UI)

## สรุป

ทดสอบครบ 6/6 TC ในขอบเขตที่ได้รับมอบหมาย (TC-027–TC-032) — **ผ่าน 5 ข้อ, บล็อก 1 ข้อ (TC-030 ทดสอบอีเมลจริงไม่ได้ แต่ทดสอบกลไกทดแทนสำเร็จ)** ไม่พบบั๊กที่ทำให้ Acceptance Criteria ไม่เป็นจริง ระบบสมัคร/อนุมัติ/ปฏิเสธบัญชีนิสิตใหม่ (BL-019, BL-020) ทำงานถูกต้องครบทั้ง flow ตั้งแต่สมัคร → เข้าคิวรออนุมัติพร้อมแจ้งเตือนอาจารย์ (แบบแบนเนอร์จำลอง) → อนุมัติแล้วใช้งานฟีเจอร์หลักได้จริง (ยืนยันด้วยการส่งผลงานจริงสำเร็จ) → ปฏิเสธแล้วเข้าใช้งานไม่ได้พร้อมแจ้งเหตุผลชัดเจนและสม่ำเสมอ **จุดที่ต้องระวังเป็นพิเศษ (ข้อความแจ้งบัญชีถูกปฏิเสธ TC-029/TC-032) ผ่านการทดสอบอย่างละเอียดแล้วไม่พบรูปแบบบั๊กเดียวกับที่เคยเจอซ้ำ 2 ครั้งในรอบก่อน** — เอกสารสถานะ backlog ของ BL-019 (`เสร็จแล้ว`) ตรงกับพฤติกรรมจริงที่ทดสอบ ส่วน BL-020 (`ทำบางส่วน` เพราะ AC ข้อแจ้งเตือนอีเมลยังไม่ implement) ก็ตรงกับพฤติกรรมจริงเช่นกัน — ไม่มีข้อเสนอแนะให้แก้ backlog status เพิ่มเติมจากที่มีอยู่แล้ว
