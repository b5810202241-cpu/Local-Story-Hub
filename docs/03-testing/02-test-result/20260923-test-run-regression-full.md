# ผลทดสอบ — Regression เต็มรูปแบบ ทุก Test Case (TC-001 ถึง TC-036 + TC-M-001)

ทดสอบผ่านเบราว์เซอร์จริง (Playwright MCP) กับเว็บที่ deploy จริงที่ [https://lsh-nammon.web.app/](https://lsh-nammon.web.app/) (production Firebase project `lsh-nammon`) — รอบนี้เป็น **regression test เต็มรูปแบบ** ตามคำขอผู้ใช้: ทดสอบ **ทุกแถว** ใน [[../01-test-plan/test-plan|test-plan]] ใหม่ทั้งหมด 37 ข้อ (TC-001–TC-036 + TC-M-001) ไม่ใช่แค่แถวที่ "ยังไม่ทดสอบ" — เพื่อยืนยันซ้ำว่าแถวที่เคย "ผ่าน" จากรอบทดสอบก่อนหน้า (7 รอบย่อยเมื่อ 2026-09-23 เช้า) ยังทำงานถูกต้องอยู่จริงกับเว็บ production ปัจจุบัน

- **วันที่ทดสอบ**: 2026-09-23 (ช่วงเวลาประมาณ 19:31–19:50 ตามเวลาเครื่อง)
- **ผู้ทดสอบ**: QA agent (จำลองผู้ใช้มือใหม่ ทดสอบผ่าน UI จริงทั้งหมด ไม่อ่าน source code เพื่อสรุปผล — อ่าน source code ของ `LSH/firestore.rules` เท่านั้นตอนอ้างอิงพฤติกรรมสิทธิ์ที่รู้อยู่แล้ว ไม่ได้ใช้ตัดสินผล)
- **บัญชีที่ใช้**: ผสมผสานระหว่างบัญชีสาธิตเดิม (`LSH/DEMO_CREDENTIALS.md`), บัญชีทดสอบที่มีอยู่แล้วจากรอบก่อน (พบว่า browser profile ของ Playwright MCP เป็นแบบ persistent — ยังมี session ค้างจากรอบทดสอบเช้าเดียวกัน) และบัญชีทดสอบใหม่ที่สร้างเพิ่มเพื่อให้ "When" ของแต่ละ TC เป็นการกระทำจริงในรอบนี้ ไม่ใช่แค่ดูข้อมูลเก่าเฉยๆ — ดูรายละเอียดครบในหัวข้อ "ข้อมูลทดสอบที่สร้างไว้ในระบบ"
- **ข้อสังเกตสำคัญเกี่ยวกับ environment**: browser ที่ Playwright MCP ควบคุมมี localStorage/Firebase Auth session ค้างข้ามรอบการทดสอบ (ไม่ใช่ browser สะอาดใหม่ทุกครั้ง) — สิ่งนี้กระทบ TC-001/002/003 โดยตรง (ดูรายละเอียดในตาราง) เพราะไม่มีเครื่องมือเคลียร์ storage ให้ใช้โดยไม่ผิดกฎห้าม JS injection

## บั๊กที่พบ (เรียงตามความรุนแรง)

### [สูง] TC-006 / BL-010 — เอกสารสถานะอ้างว่ามี UI ปักหมุดตำแหน่งจริงบน production แต่ทดสอบจริงไม่พบเลย

**รายละเอียดเต็มอยู่ในแถว TC-006 ด้านบน** สรุปสั้น: `CLAUDE.md` หัวข้อ "ตำแหน่งบนแผนที่ — BL-010" (อัปเดต 2026-09-23 รอบสาม ซึ่งเป็นเอกสารกำกับงานของ QA รอบนี้โดยตรง) ระบุชัดเจนว่า:

- เพิ่ม UI ปักหมุดจริงด้วย Leaflet + OpenStreetMap ใน `student-publish.html` และ `community-create-content.html` แล้ว
- ทดสอบ end-to-end ผ่านจริง (login จริง, ปักหมุดจริง, ส่งจริง, อาจารย์อนุมัติจริง, แสดงผลถูกต้องครบทุกหน้า)
- **"deploy ได้ทันทีไม่มีขั้นตอนที่ผู้ใช้ต้องทำเพิ่ม"**
- **"BL-010 ปิดสถานะเป็นเสร็จแล้ว"**

ทดสอบจริงบน production (`https://lsh-nammon.web.app/`) วันเดียวกันพบว่า **ไม่มี UI ปักหมุด/แผนที่ปรากฏเลยแม้แต่นิดเดียว** ทั้งในฟอร์มสร้างผลงานนิสิตและฟอร์มสร้างคอนเทนต์ชุมชน (ตรวจด้วย `browser_find` หาคำว่า "ปักหมุด"/"แผนที่"/"ตำแหน่ง" ไม่พบ, ตรวจ network requests ไม่พบการโหลด Leaflet library เลย) เนื้อหาทดสอบที่ตั้งชื่อว่า "[AUTOTEST-BL010] ทดสอบปักหมุดตำแหน่ง" ที่มีอยู่ในระบบก็ไม่มีข้อมูลพิกัดบันทึกไว้จริง (แสดง fallback ข้อความเดิมเหมือนเนื้อหาที่ไม่เกี่ยวกับ BL-010 เลย)

**ข้อสันนิษฐานที่เป็นไปได้** (ไม่ยืนยัน เพราะ QA ไม่อ่าน source code เพื่อสืบสวน): การ testing "จริง" ที่ CLAUDE.md อ้างถึงอาจทำผ่าน **local dev server** (เชื่อมกับ Firestore project เดียวกัน) แล้วไม่เคยถูก deploy ไฟล์ HTML/JS จริงขึ้น Firebase Hosting (`firebase deploy --only hosting`) หรือมีการ deploy แล้วแต่ไฟล์ถูก revert/overwrite ทีหลัง — ไม่ว่าสาเหตุจะเป็นอะไร **ผลลัพธ์คือฟีเจอร์ที่เอกสารบอกว่า "เสร็จแล้ว" ใช้งานจริงบน production ไม่ได้เลย**

**ผลกระทบ**: ผู้ใช้จริง (นิสิต/ชุมชน) ไม่มีทางปักหมุดตำแหน่งได้เลยตามที่เอกสารสัญญาไว้ นักท่องเที่ยวยังคงได้แค่ workaround แบบเดิม (ลิงก์ Google Maps ค้นหาด้วยชื่อชุมชน ไม่ใช่พิกัดจริง) — Acceptance Criteria ของ BL-010 (Priority: Should) ยังไม่บรรลุจริงบน production แม้ backlog/CLAUDE.md จะระบุว่าเสร็จแล้ว

**คำแนะนำ**: ทีมพัฒนาควรตรวจสอบว่า `firebase deploy --only hosting` ถูกรันจริงหลังแก้โค้ด BL-010 หรือไม่ (รันจาก root ของ repo เท่านั้นตามที่ระบุใน `CLAUDE.md`) และตรวจว่าไฟล์ `student-publish.html`/`community-create-content.html` บน `docs/02-design/01-prototypes/prototype-v2/` local มีโค้ด Leaflet จริงหรือไม่ก่อนแก้ไขสถานะเอกสารให้ตรงกับพฤติกรรมจริง

## สรุป

ทดสอบครบ **37/37 TC** (TC-001–TC-036 + TC-M-001) ตามที่ได้รับมอบหมาย — **ผ่าน 25 ข้อ, ไม่ผ่าน (พบบั๊ก) 1 ข้อ (TC-006 — ความรุนแรงสูง, เอกสารสถานะ BL-010 ไม่ตรงกับพฤติกรรมจริงบน production), บล็อก 9 ข้อ (TC-001, 002, 003, 005, 012, 013, 014, 015, 030 — ทุกข้อมีเหตุผลชัดเจนไม่ใช่บั๊กใหม่ ยกเว้น TC-001/002 ที่บล็อกเพราะข้อจำกัดของ browser profile รอบนี้เอง), ข้าม 2 ข้อ (TC-010, TC-011 — BL-001 ยังไม่เริ่ม implement)**

**จุดเด่นของรอบนี้เทียบกับรอบเช้า**:
1. **ยืนยันซ้ำสำเร็จว่าบั๊กที่เคยพบ 2 ตัว (TC-022, TC-026) ยังคงแก้ไขอยู่จริงบน production** — ไม่ regression กลับไปเป็นบั๊กเดิม
2. **พบ regression ใหม่ที่สำคัญ 1 จุด**: BL-010 (TC-006) — CLAUDE.md ของรอบนี้อ้างว่าเพิ่ม UI ปักหมุดจริงแล้วและปิดสถานะเป็น "เสร็จแล้ว" แต่ production **ไม่มี UI นี้อยู่เลย** เป็นตัวอย่างชัดเจนของ "เอกสารบอกว่าเสร็จแล้วแต่ทดสอบจริงพบว่าใช้งานไม่ได้เลย" ตามกฎ QA ที่ต้องถือเป็นบั๊กความรุนแรงสูง
3. TC-001/TC-002 ที่เคย "ผ่าน" ในรอบเช้า **ไม่สามารถยืนยันซ้ำได้ในรอบนี้** เพราะข้อจำกัดของ browser profile ที่ persistent ข้ามรอบทดสอบ — แนะนำให้รอบถัดไปทดสอบด้วย browser profile ใหม่ที่สะอาด (หรือจัดหาเครื่องมือ clear storage ที่ไม่ใช่ JS injection) เพื่อปิดช่องว่างนี้

ระบบโดยรวมยังคงทำงานถูกต้องตาม Acceptance Criteria ในเกือบทุกจุดที่ทดสอบได้ ยกเว้นจุดที่ระบุไว้ข้างต้น — คำแนะนำหลักสำหรับทีมพัฒนาคือ**ตรวจสอบและแก้ไขสถานะการ deploy ของ BL-010 ให้ตรงกับพฤติกรรมจริงบน production โดยเร็ว** เพราะเอกสารปัจจุบันทำให้ผู้ใช้/ผู้มีส่วนได้ส่วนเสียเข้าใจผิดว่าฟีเจอร์นี้ใช้งานได้แล้ว
