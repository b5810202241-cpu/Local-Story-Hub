ทดสอบผ่านเบราว์เซอร์จริง (Playwright MCP) กับเว็บที่ deploy จริงที่ [https://lsh-nammon.web.app/](https://lsh-nammon.web.app/) (production Firebase project `lsh-nammon`) ตามขอบเขตที่ได้รับมอบหมาย — เฉพาะ **TC-023 ถึง TC-026** (หมวด "นิสิตนิเทศศาสตร์") ใน [[../01-test-plan/test-plan|test-plan]] เท่านั้น จุดเน้นพิเศษของรอบนี้คือการ retest dropdown "เลือกชุมชนที่เกี่ยวข้อง" ใน `student-publish.html` (BL-013) ที่เพิ่งแก้ให้ดึงรายชื่อชุมชนจริงจาก Firestore และ deploy `firestore.rules` ไปแล้ว แต่ยังไม่เคย retest จริงผ่านเบราว์เซอร์เลยหลัง deploy (มีบันทึกค้างไว้ใน `docs/05-log/index.md`)

- **วันที่ทดสอบ**: 2026-09-23
- **ผู้ทดสอบ**: QA agent (จำลองผู้ใช้มือใหม่ ทดสอบผ่าน UI จริงทั้งหมด ไม่อ่าน source code เพื่อสรุปผล — อ่าน source code เฉพาะตอนสืบสวนบั๊กหลังพบความผิดปกติจาก UI แล้วเท่านั้น)
- **บัญชีทดสอบที่ใช้**: บัญชีนิสิตสาธิต `u001@example.com` (แสนสวย ร่ำรวยเสน่ห์) และ `u002@example.com` (มิลเลียน น่ารัก) จาก `LSH/DEMO_CREDENTIALS.md`, บัญชีอาจารย์ `u004@example.com` สำหรับอนุมัติ/ไม่อนุมัติ — ทั้งหมด login ได้สำเร็จไม่ต้องสมัครใหม่

## ผลการตรวจ dropdown "เลือกชุมชนที่เกี่ยวข้อง" (BL-013) — จุดเน้นพิเศษของรอบนี้

**สรุป: ผ่านครบทั้ง 3 ข้อที่ต้องตรวจ**

1. **โหลดรายชื่อชุมชนจริงจาก Firestore ได้ไม่มี error "Missing or insufficient permissions"** — login ด้วยบัญชีนิสิต `u001@example.com` แล้วเปิด `student-publish.html` dropdown แสดงรายชื่อชุมชนจริงทันที (`option` 3 รายการ) ไม่มี badge DRAFT ค้างอยู่แล้ว (ตรงตามที่บันทึกไว้ว่าถูกลบออกแล้ว) ตรวจ `browser_console_messages` (ทุก level รวม debug) และ `browser_network_requests` (filter `firestore`) ครบทุก request ที่เกี่ยวกับ `users`/`LSHRequests` — **ไม่พบ error ใดๆ เลย ไม่มี `permission-denied`/`Missing or insufficient permissions`** ยืนยันว่า `firestore.rules` ที่ deploy ไปแก้ gap ได้จริง (rule OR clause ให้นิสิต query บัญชีชุมชน `role=='community' && status=='อนุมัติแล้ว'` ได้ ทำงานถูกต้อง)
2. **รายชื่อที่โชว์ตรงกับบัญชีชุมชนที่อนุมัติแล้วจริงในระบบ** — dropdown แสดงครบทั้ง 3 รายการตามที่คาด: `ชุมชนทดสอบผาบ่อง QA`, `ทดสอบ QA ชุมชนบ้านผาบ่อง 2`, `ทดสอบ QA ชุมชนอนุมัติ` (ตรงกับบัญชีชุมชนที่อนุมัติแล้วจากรอบทดสอบก่อนหน้าทุกรายการ ไม่ขาด ไม่เกิน)
3. **เลือกชุมชนแล้วส่งผลงานได้จริง ชุมชนที่เลือกถูกบันทึกและแสดงถูกต้อง** — ทดสอบ 2 รอบแยกกัน (เลือก "ทดสอบ QA ชุมชนอนุมัติ" สำหรับ TC-023/024/025, เลือก "ทดสอบ QA ชุมชนบ้านผาบ่อง 2" สำหรับ TC-026) ยืนยันว่าชื่อชุมชนที่เลือกถูกบันทึกลง Firestore (field `community` บน `LSHRequests`) ถูกต้องและแสดงตรงกันทุกจุดที่ตรวจสอบ: หน้าอาจารย์ (การ์ดที่รออนุมัติ + ตารางประวัติหลังอนุมัติ/ไม่อนุมัติ), หน้าสาธารณะ `published-works.html` (ไม่ต้อง login), และหน้า `tourist-search-results.html` (ไม่ต้อง login) — ตรวจซ้ำหลัง refresh หน้าทุกจุดที่มีการเขียนข้อมูล ผลลัพธ์คงเดิมทุกครั้ง

**สรุปข้อ (ก)(ข)(ค) ที่ระบุไว้ในขอบเขตงาน — ผ่านครบทั้ง 3 ข้อ ยืนยัน BL-013 ทำงานได้จริง end-to-end แล้วหลัง deploy**

## บั๊กที่พบ

- **[ปานกลาง] ระบบไม่แจ้งเหตุผลการไม่อนุมัติผลงานกลับไปยังนิสิตเลย (ครึ่งหลังของ Then ของ TC-026 ไม่เป็นจริง)** — Acceptance Criteria ของ BL-018 (และ Then ของ TC-026) ระบุชัดเจนว่า "ระบบไม่เผยแพร่ผลงานนั้น **และแจ้งเหตุผลกลับไปยังนิสิต**" แต่ทดสอบจริงพบว่าเมื่ออาจารย์กด "ไม่อนุมัติ" ผลงาน ฝั่งนิสิตไม่มีทางรับรู้เลยว่าผลงานถูกปฏิเสธ ไม่ต้องพูดถึงเหตุผล — ตรวจสอบ source code ยืนยันสาเหตุ: `docs/02-design/01-prototypes/prototype-v2/student-publish.html` มีแค่ `addDoc(collection(db, 'LSHRequests'), ...)` (บรรทัด 367) เพื่อเขียนผลงานใหม่เท่านั้น **ไม่มีจุดใดในไฟล์นี้เลยที่ query กลับมาอ่านผลงานเดิมของนิสิตคนนั้น** (ไม่มี `where('requesterId','==', currentProfile.id)` หรือ query ลักษณะเดียวกันบน `LSHRequests` เลยทั้งไฟล์) ส่วนที่อ่าน `rejectionReason` กลับมาแสดง (บรรทัด 279-280) เป็นของ **บัญชีผู้ใช้ (`users` collection)** เท่านั้น (กรณีบัญชีนิสิตถูกปฏิเสธตอนสมัคร ไม่ใช่กรณีผลงานถูกปฏิเสธ) — เหตุผลที่อาจารย์กรอกไว้ถูกเก็บและแสดงถูกต้องเฉพาะในตาราง "ประวัติการตรวจสอบ" ของหน้าอาจารย์เท่านั้น (ฝั่งเดียว) — ผลกระทบ: นิสิตที่ถูกปฏิเสธผลงานจะไม่รู้เลยว่าผลงานของตนถูกปฏิเสธหรือทำไมถึงถูกปฏิเสธ นอกจากจะไปถามอาจารย์โดยตรงนอกระบบ ทำให้ไม่สามารถแก้ไขและส่งใหม่ได้อย่างมีข้อมูลประกอบ (ทั้งที่ Business Rule ปิด Open Question ไว้แล้วว่าส่งใหม่ได้ไม่จำกัดจำนวนครั้ง) — ไม่กระทบความปลอดภัย/ความถูกต้องของข้อมูล (ผลงานจริงไม่ถูกเผยแพร่อย่างถูกต้อง) จึงไม่ใช่บั๊กความรุนแรงสูง แต่กระทบ UX/การสื่อสารตรงตาม Acceptance Criteria ที่ระบุไว้ชัดเจน **เป็นรูปแบบบั๊กเดียวกันเป๊ะกับที่พบในรอบทดสอบ TC-022 (ชุมชน-ขอแก้ไข คอนเทนต์, ดู [[20260923-test-run-community-edit-request|20260923-test-run-community-edit-request]])** — ทั้งสองจุดขาด UI/query ฝั่งผู้ส่งคำขอที่แสดงประวัติ+เหตุผลของคำขอที่ถูกปฏิเสธ แนะนำให้ทีมพัฒนาแก้พร้อมกันทั้งสองจุดโดยรูปแบบเดียวกัน เช่น เพิ่ม section "ประวัติผลงานที่เคยส่ง" ใน `student-publish.html` ที่ query `LSHRequests` ด้วย `where('requesterId','==', currentProfile.id)` แสดงสถานะ+เหตุผล (ถ้ามี) ของทุกผลงานที่เคยส่ง

## สรุป

ทดสอบครบ 4/4 TC ในขอบเขตที่ได้รับมอบหมาย (TC-023–TC-026) — **ผ่าน 3 ข้อ (TC-023, TC-024, TC-025), ไม่ผ่าน 1 ข้อ (TC-026)** จุดเน้นพิเศษของรอบนี้คือการ retest dropdown "เลือกชุมชนที่เกี่ยวข้อง" (BL-013) หลัง deploy `firestore.rules` — **ยืนยันผ่านแล้ว end-to-end เต็มรูปแบบ ปิดช่องว่างที่ค้างไว้ในบันทึกก่อนหน้าได้สำเร็จ** ไม่พบ error "Missing or insufficient permissions" เลยตลอดการทดสอบ รายชื่อชุมชนที่แสดงตรงกับบัญชีชุมชนที่อนุมัติแล้วจริงในระบบครบถ้วน และชุมชนที่เลือกถูกบันทึก+แสดงผลถูกต้องทั้งหน้าอาจารย์/หน้าสาธารณะ/หน้านักท่องเที่ยว — **BL-013 ถือว่าเสร็จสมบูรณ์เต็มรูปแบบแล้วจากมุมมองการทดสอบนี้** แต่พบบั๊กความรุนแรงปานกลาง 1 รายการที่ TC-026 (BL-018): ระบบไม่แจ้งเหตุผลการไม่อนุมัติผลงานกลับไปยังนิสิตเลยตามที่ Acceptance Criteria ระบุไว้ชัดเจน (ไม่มี UI ฝั่งนิสิตจุดใดแสดงผลงานที่ถูกปฏิเสธหรือเหตุผล) เป็นรูปแบบบั๊กเดียวกันกับที่พบในรอบทดสอบ TC-022 ก่อนหน้า — เอกสารสถานะ backlog ของ BL-018 ควรได้รับการทบทวนเพราะส่วน "แจ้งเหตุผลกลับไปยังนิสิต" ของ Acceptance Criteria ยังไม่ได้ implement จริง
