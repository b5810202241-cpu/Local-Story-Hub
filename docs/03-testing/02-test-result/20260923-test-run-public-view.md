## รายละเอียดการทดสอบ TC-035 (Security Test — เจาะลึกเป็นพิเศษ)

เตรียมข้อมูลทดสอบเอง (ผ่าน UI ปกติ ไม่แตะ backend ตรง): login ด้วยบัญชีนิสิต `u001@example.com` สร้างผลงานใหม่ชื่อ "ทดสอบ QA - ผลงานนิสิต TC-035 (รอพิจารณา ห้ามเข้าถึงแบบ public)" — บันทึกลง Firestore ด้วย document ID **`74eCxoxJ2NXoCN8gTk2Q`** ในสถานะเริ่มต้น "รอพิจารณา" (ตรวจสอบ ID จริงจาก request body ของการเขียนข้อมูลผ่าน `browser_network_request`, ไม่ได้เดา) จากนั้น login ด้วยบัญชีอาจารย์ `u004@example.com` กด "ไม่อนุมัติ" เปลี่ยนสถานะผลงานเดียวกันนี้เป็น "ไม่อนุมัติ" พร้อมเหตุผล เพื่อให้มีข้อมูลทดสอบครบทั้ง 2 สถานะที่ Acceptance Criteria ระบุ (**"รอพิจารณา" หรือ "ไม่อนุมัติ"**) แล้ว logout ออกจากทุกบัญชีก่อนเริ่มทดสอบ TC-035 จริงในฐานะบุคคลทั่วไปที่ไม่ login

ทดสอบทั้ง 3 ช่องทางตามที่ได้รับมอบหมาย ทำซ้ำทั้งตอนสถานะ "รอพิจารณา" และหลังเปลี่ยนเป็น "ไม่อนุมัติ":

**(ก) เดา/สร้าง URL ตรงไปที่หน้ารายละเอียด**: ระบบมีหน้ารายละเอียดแยก (`tourist-story-detail.html?type=student&id=<docId>`) ที่อ่านได้แบบ public โดยไม่ login สำหรับผลงานที่เผยแพร่แล้ว — navigate ตรงไปที่ `tourist-story-detail.html?type=student&id=74eCxoxJ2NXoCN8gTk2Q` ด้วย document ID จริงที่มีอยู่จริงในระบบ (ไม่ใช่ ID สุ่ม) ทั้ง 2 รอบ (ตอนสถานะ "รอพิจารณา" และ "ไม่อนุมัติ") — **ผลลัพธ์ทั้ง 2 ครั้ง**: หน้าแสดงข้อความ `โหลดเรื่องราวไม่สำเร็จ: Missing or insufficient permissions.` เท่านั้น ไม่มีชื่อผลงาน/เนื้อหา/ข้อมูลใดๆ ของเอกสารนั้นหลุดออกมาเลยแม้แต่ตัวอักษรเดียว ตรวจ `browser_console_messages` ระดับ error พบแค่ `FirebaseError: Missing or insufficient permissions.` ไม่มีข้อมูลเอกสารรั่วในนั้นเช่นกัน — ยืนยันว่า `firestore.rules` บังคับสิทธิ์ที่ระดับ document read (ไม่ใช่แค่ระดับ query) ถูกต้อง

**(ข) ค้นหาชื่อผลงานที่ยังไม่อนุมัติในหน้าค้นหา**: ใช้ `browser_find` ค้นหาคำว่า "TC-035" ในทั้ง `published-works.html` และ `tourist-search-results.html` (พร้อมลองพิมพ์ในช่องค้นหาของ `tourist-search-results.html` ด้วย) ทั้ง 2 รอบสถานะ — **ไม่พบผลลัพธ์เลยสักครั้ง** ("No matches found for TC-035") ยืนยันว่าผลงานที่ไม่อนุมัติไม่ปรากฏในรายการ/ผลค้นหาใดๆ

**(ค) ตรวจ network requests ว่ามีข้อมูลรั่วแบบ fetch-all-then-filter หรือไม่**: ใช้ `browser_network_request` ดู request body ของ Firestore Listen channel (คำสั่ง query จริงที่เบราว์เซอร์ส่งไป) ทั้งใน `published-works.html` และ `tourist-search-results.html` — พบว่า query ที่ยิงจริงมี `structuredQuery.where.fieldFilter` กรอง `status == 'อนุมัติ'` ที่ **ฝั่ง server (Firestore เอง) ตั้งแต่ต้น** ไม่ใช่ query ที่ดึงเอกสารทั้งหมดมาก่อนแล้วค่อยกรองด้วย JS ฝั่ง client (รูปแบบข้อมูลรั่วที่ระบุไว้ในขอบเขตงานว่าต้องตรวจเป็นพิเศษ) ตัวอย่าง query จริงที่ยิงจาก `published-works.html`:
```
structuredQuery.from = [{collectionId: "LSHRequests"}]
structuredQuery.where.fieldFilter = {field: "status", op: "EQUAL", value: "อนุมัติ"}
```
และจาก `tourist-search-results.html` (ยิง 2 query คู่กัน กรองทั้งคู่ที่ server): `LSHRequests` กรอง `status == 'อนุมัติ'`, `CommunityContent` กรอง `status == 'เผยแพร่แล้ว'` — ทดสอบเพิ่มเติมด้วยการเลือก filter ชุมชนใน `published-works.html` (TC-034) แล้วตรวจว่ามี query ใหม่ยิงออกไปหรือไม่ พบว่า**ไม่มี** query ใหม่ (filter ชุมชนกรองที่ client บนชุดข้อมูลที่ server กรอง status มาแล้วเท่านั้น) ซึ่งปลอดภัยเพราะฐานข้อมูลที่ไปกรองต่อไม่เคยมีเอกสารที่ไม่อนุมัติปนอยู่เลยตั้งแต่ต้น

**สรุปข้อ (ก)(ข)(ค) — ผ่านครบทั้ง 3 ข้อ ไม่พบข้อมูลรั่วไหลแม้แต่นิดเดียวในทุกช่องทางที่ทดสอบ ทั้ง 2 สถานะ ("รอพิจารณา" และ "ไม่อนุมัติ")**

## บั๊กที่พบ

ไม่พบบั๊กในรอบทดสอบนี้ — ทั้ง 4 TC ผ่านครบถ้วนตาม Acceptance Criteria โดยเฉพาะ TC-035 ที่เป็น security test สำคัญด้าน data privacy ก็ไม่พบข้อมูลรั่วไหลเลยแม้แต่นิดเดียวหลังทดสอบอย่างละเอียดครบทั้ง 3 ช่องทางและทั้ง 2 สถานะที่เกี่ยวข้อง

## สรุป

ทดสอบครบ 4/4 TC ในขอบเขตที่ได้รับมอบหมาย (TC-033–TC-036) — **ผ่านทั้งหมด 4 ข้อ ไม่พบบั๊กเลยในรอบนี้** — จุดเน้นพิเศษ TC-035 (security test เรื่องการเข้าถึงผลงานที่ยังไม่อนุมัติ) ทดสอบอย่างละเอียดครบทั้ง 3 ช่องทาง (URL ตรง/ค้นหา/ตรวจ network query) และครบทั้ง 2 สถานะที่เกี่ยวข้อง ("รอพิจารณา"/"ไม่อนุมัติ") **ไม่พบข้อมูลรั่วไหลแม้แต่นิดเดียว** — ยืนยันว่า `firestore.rules` บังคับสิทธิ์ที่ระดับ document read ถูกต้อง (ไม่ใช่แค่ระดับ query) และทุก query ฝั่ง public ใช้รูปแบบ server-side filter (`where status == 'อนุมัติ'`) ตั้งแต่ต้น ไม่มีรูปแบบ fetch-all-then-filter-on-client ที่จะทำให้ข้อมูลหลุดออกมาได้ — **BL-021 ถือว่าเสร็จสมบูรณ์และปลอดภัยจากมุมมองการทดสอบนี้** รอบนี้เป็น**รอบทดสอบสุดท้าย** ปิด test plan ให้ครบทั้ง **36/36 ข้อ** (ดูสรุปภาพรวมทั้งโปรเจกต์ใน [[../01-test-plan/test-plan|test-plan]] § สรุป และ [[../../05-log/index|05-log]])
